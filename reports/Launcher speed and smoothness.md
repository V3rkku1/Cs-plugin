# Unblock the main thread, then lazy-load pages

The launcher gets most of its startup and smoothness gains from about six changes, and none of them needs a new dependency. In priority order: **move the item-database load off the Tauri main thread and parse it in one pass** (`src/Launcher/src/api/mod.rs:117`, `src/Launcher/src/itemdb.rs:152-191`, `src/Launcher/src/util.rs:100-104`). **Show the window only after the page has painted, and set the background colour on the builder** (`src/Launcher/src/main.rs:189`). **Seed the saved page and theme from `localStorage` before the first `render()`**, which removes the Play-page flash and the theme flash on every start (`src/Launcher/web/js/app.js:114-117`). **Lazy-load the 8 non-Play pages**, which takes roughly 250 KB of the 316 KB of JS off the critical path (`src/Launcher/web/js/app.js:8-16`). **Deduplicate `useApi` refetches and skip re-renders when the data has not changed** (`src/Launcher/web/js/api.js:52-71`). **Drop `backdrop-filter` where it blurs nothing** (`src/Launcher/web/css/glass.css:41-43,380-407`). After that, the backend's 1-second poll holds the global `State` lock across process enumeration and file reads, so IPC calls stall behind it. Fixing that is the main remaining source of UI jitter. Every impact figure here comes from reading the code, not from measurement. No release build was profiled, nobody took a WebView2 trace, and the on-disk size of the item-DB cache and of real inventories is unknown. Treat the ranking as a strong prior and confirm it with a release-build measurement. The Tauri team says debug builds are much slower for IPC, so debug timings would mislead ([tauri discussion #5511](https://github.com/orgs/tauri-apps/discussions/5511)). Two popular "free wins" are not free here. `panic = "abort"` would turn any IPC-worker panic into a crash of the whole launcher. WebView2 GPU flags in `additionalBrowserArgs` have no documented startup benefit.

## Startup cost lies on two critical paths, and both are serial today

Before the window appears, the Tauri `setup` closure runs on the main thread. It reads `launcher.json` and then **8 item-database JSON files one after another**, builds two HashMap indexes, and only then creates the window ([main.rs:238-241](../src/Launcher/src/main.rs), [itemdb.rs:152-191](../src/Launcher/src/itemdb.rs)). Each file goes through `util::read_json`. That function parses into a `serde_json::Value`, walks it to strip nulls, then runs `from_value`: **two full passes plus a DOM allocation for every value** ([util.rs:100-104](../src/Launcher/src/util.rs)). The code says the full download writes about 25 MB. Nobody knows how large the cache is on a user's disk, so the gain here could be tens of ms or several hundred. Next, the window is resized and re-centred after `build()`, possibly moved again from saved settings, and maximized. It is then shown with `window.show()` at once. Nothing waits for the page to load, and `fit_zoom` runs after `show()`, so a large window visibly re-zooms right after its first paint ([main.rs:124-191](../src/Launcher/src/main.rs)). The background colour is set in `apply_title_bar` after build, never on the builder ([api/theme.rs:241-247](../src/Launcher/src/api/theme.rs)). WebView2's default surface is white, and setting the window background colour is the documented fix for the white flash ([queryden #75](https://github.com/openidle-dev/queryden/issues/75), [Nembrix PR #110](https://github.com/Nembrix/nembrix/pull/110)).

The page then has its own waterfall. `index.html` loads 4 render-blocking stylesheets and one module, `js/app.js`, with no preload hints ([index.html:7-10,16](../src/Launcher/web/index.html)). `app.js` statically imports **all 9 pages** ([app.js:8-16](../src/Launcher/web/js/app.js)), and through them `lineups-data.js` (49 KB of data), `inventory.js` (57 KB) and `live.js` (35 KB). The browser finds each import level only after it parses the level above. Microsoft's WebView2 guidance names exactly this trap: with an SPA, "the entire framework code must be downloaded, parsed, and run, before anything can be displayed". It advises deferring heavy components until after the first UI appears ([MS Learn: WebView2 performance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)). When the first frame finally renders, it renders the wrong thing. `page` starts as `null`, so `PlayPage` mounts and fires its own calls. When `app.state` returns, the effect swaps to the saved page. The theme is likewise applied only after `setup.state` returns, so the first frames use the hard-coded `:root` colours ([app.js:114-117](../src/Launcher/web/js/app.js), [theme.js:29-55](../src/Launcher/web/js/theme.js)). All of this happens while about 6 IPC calls start at once, including the heavy `cases.inventory` prefetch ([app.js:120](../src/Launcher/web/js/app.js)). At the same moment, the backend's `api::started` thread **holds the global `State` mutex while it scans for CS2**, writes settings, maybe rewrites `skins.json`, and reparses `gamemodes.txt` ([api/shell.rs:190-203](../src/Launcher/src/api/shell.rs), [api/mod.rs:260-278](../src/Launcher/src/api/mod.rs)). The page's first data calls queue behind that lock.

## Six fixes deliver most of the gain at low effort

The table ranks fixes by impact and effort together. "Effort" means lines changed and risk, not hours. Every impact entry is an estimate from the code.

| # | Fix | Where | Impact | Effort | Measured? |
|---|-----|-------|--------|--------|-----------|
| 1 | Start with `ItemDatabase::default()`, load the DB in the `started` thread, swap it in and emit `changed`. The swap pattern already exists. Parse with `serde_json::from_slice` and fall back to `read_json` only on error. | `api/mod.rs:117`, `api/mod.rs:280-291`, `itemdb.rs:152-191`, `util.rs:100-104` | High: time to window | Low-Med | No (cache size unknown) |
| 2 | Pass the theme colour to `WebviewWindowBuilder::background_color`. Add an inline `<style>html,body{background:…;color-scheme:dark}</style>` to `index.html`. Move `fit_zoom` to before `show()`. | `main.rs:126-150,189-191`, `index.html` | High: perceived (no white flash, no zoom jump) | Low | No |
| 3 | Write `page` and the theme to `localStorage` on change, and read them synchronously before `render()`. Reuse the try/catch pattern at `app.js:40`. | `app.js:114-117,154`, `theme.js:29-55` | Medium-High: removes the page and theme flash and one wasted mount | Low | No |
| 4 | Keep `PlayPage` static and load the other pages with `import()`. Warm them with `requestIdleCallback` after first paint. Load `lineups-data.js` on demand inside Trainer. | `app.js:8-16`, `trainer.js:7` | High: about 250 KB of JS off the critical path | Medium | Sizes measured; timing not |
| 5 | `useApi`: one in-flight promise and one subscription per `cacheKey`. Skip `setData` when the JSON string is unchanged, as `live.js:82` already does. | `api.js:52-71` | High: smoothness after every `changed` and `play.tick` | Low-Med | No |
| 6 | Default `.glass` to `backdrop-filter:none` and enable it only when opacity < 100. Make `.btn` use `var(--glass-blur)`. | `glass.css:41-43,121-147,380-407`, `theme.js:41-42` | High: scroll and animation smoothness | Low | No (inferred Chromium behaviour) |
| 7 | `poll_server`, `watch_game`, `friends::beacon`: compute `test_mode_on()` once per tick, cache `find_server()` for about 1 s, and do file and process I/O outside the `State` lock. | `api/play.rs:634-658`, `session.rs:112-135,201-205`, `api/shell.rs:455-488`, `api/friends.rs:557-574` | High: IPC jitter and idle CPU | Medium | No |
| 8 | `api::started`: compute discovery results without the lock, then lock only to assign them. | `api/shell.rs:190-203`, `api/mod.rs:260-278` | Medium: first data paint | Low | No |
| 9 | Inventory: `useMemo` the filter, the sort and `grades`; debounce `q` (copy `inventory.js:521-525`); add `content-visibility:auto` to `.cs-item`. | `inventory.js:684-737`, `glass.css:809-815` | High for large inventories | Low | No (inventory size unknown) |
| 10 | Stop the page re-rendering on every App state change. Move `useApi("app.state"/"setup.state")` out of `App` into `Sidebar`, `UpdatePopup` and a small appearance component. | `app.js:112-173` | Medium-High | Medium | No |

Fix 1 is the only change that shortens time to window by real wall-clock time. Everything that comes after `setup` is already off the main thread. A real Tauri app (Nembrix) used fixes 2 and 3 together: a window `backgroundColor`, an inline dark background in `index.html`, and state hydration moved to before the first `render()` to stop a content blink ([Nembrix PR #110](https://github.com/Nembrix/nembrix/pull/110)). For fix 2, the safest way to "show when ready" is a Rust-side `on_page_load(Finished)` hook, or an `app.ready` call into the existing `call` command, plus a 1–2 s fallback timer. Without the timer, a JS error leaves an invisible app. Calling `getCurrentWindow().show()` from JS would also need `core:window:allow-show`, because the capabilities grant only `core:default` ([capabilities/default.json:1-6](../src/Launcher/capabilities/default.json)). A Tauri bug report says calling `show()` from inside `setup()` with `visible:false` made later child windows misbehave ([tauri #9286](https://github.com/tauri-apps/tauri/issues/9286)). The launcher has only one window, but that is a reason to show from page-load rather than from `setup`. Fix 10 cannot use `memo`, because the vendored `vendor/preact-htm.js` exports `Component` and the hooks but **no `memo`**. The two options are to move the state down the tree as described, or to wrap the page in a small `Component` with `shouldComponentUpdate(){return false}`.

## The second tier smooths the steady state, not the launch

When the app is idle, the 1-second poll thread holds `State` while it reads the plugin status file with the double parse. It also builds a fresh `sysinfo::System` for each `find_server()`, and reads `gameinfo.gi` 2–4 times through repeated `test_mode_on()` calls ([api/play.rs:634-658](../src/Launcher/src/api/play.rs), [session.rs:112-135](../src/Launcher/src/session.rs), [api/mod.rs:104-111](../src/Launcher/src/api/mod.rs)). On the frontend, every backend `changed` event (emitted from about 75 sites) makes **every mounted `useApi` hook refetch with no deduplication**, and replaces the data even when it is identical ([api/mod.rs:167-170](../src/Launcher/src/api/mod.rs), [api.js:52-71](../src/Launcher/web/js/api.js)). `play.tick` also reloads Play, Friends, Trainer and Stats data ([play.js:13,62](../src/Launcher/web/js/pages/play.js), [stats.js:226](../src/Launcher/web/js/pages/stats.js)). Together, fixes 5 and 7 turn each event into one cheap call per distinct key, with no lock wait and no re-render when nothing changed. Giving `changed` a scope (`"inventory"`, `"setup"`, `"play"`) is the follow-up step. It touches about 75 emit sites, so its effort is higher.

Several smaller items are worth batching into one cleanup pass. `cases.inventory` re-reads `loadout.json` and `inventory-removed.json` on every call, and calls `prices.ensure()` once per item ([api/cases.rs:531-549](../src/Launcher/src/api/cases.rs), [api/cases.rs:213-216](../src/Launcher/src/api/cases.rs)). Cache the loadout by mtime and call `ensure()` once per request. `Inv::save` rewrites the whole inventory on every case open while holding both locks ([api/cases.rs:134-142](../src/Launcher/src/api/cases.rs)). Coalescing that write is medium effort, and it touches data-loss behaviour, so it needs a test. The `lst://` image protocol spawns one OS thread per request, about 100 threads for a 100-thumbnail grid ([main.rs:230-236](../src/Launcher/src/main.rs), [media.rs:10-43](../src/Launcher/src/media.rs)). `tauri::async_runtime::spawn_blocking` is the bounded executor already used for `call` ([main.rs:42-52](../src/Launcher/src/main.rs)). The shared ureq agent has a 300 s timeout, so a stalled image can hold one of the 6 download slots for 5 minutes ([util.rs:124-131](../src/Launcher/src/util.rs)). The UDP listener enumerates every NIC once per packet ([net.rs:660](../src/Launcher/src/net.rs)). On the CSS side, the case reel rewrites `filter: blur` on a large image strip every frame ([cases.js:118-132](../src/Launcher/web/js/pages/cases.js)). The winner glow animates `box-shadow` without end, and the Segmented thumb transitions `width/height` ([glass.css:852-853,460](../src/Launcher/web/css/glass.css)). Animating only `transform` and `opacity` is the standard remedy, and Microsoft's WebView2 page tells apps to prefer CSS animation and avoid layout thrashing ([MS Learn](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)). `content-visibility:auto` cut rendering from 232 ms to 30 ms in web.dev's demo ([web.dev](https://web.dev/articles/content-visibility)). It is the cheapest relief for the drop-shadowed Inventory grid, short of virtualization. Finally, `watchCustomCss()` refetches `custom.css` and restyles the whole document on every window `focus` ([theme.js:57-68](../src/Launcher/web/js/theme.js)). `app.page` writes the settings file on every page switch ([api/shell.rs:72-87](../src/Launcher/src/api/shell.rs)). The `newer()` regex is recompiled on every Setup render ([api/setup.rs:266-279](../src/Launcher/src/api/setup.rs)). Each of these is a one- or two-line fix with small gains.

## Popular build-flag tweaks matter least, and two carry real risk

Tauri's recommended release profile is `codegen-units = 1`, `lto = true`, `opt-level = "s"` and `panic = "abort"` ([Tauri: App size](https://v2.tauri.app/concept/size/)). The launcher uses `"s"`, thin LTO, default codegen units and unwind ([Cargo.toml:39-43](../src/Launcher/Cargo.toml)), and the comment there shows that thin LTO was chosen on purpose for build speed. **Do not adopt `panic = "abort"` blindly.** `App::state()` recovers from a poisoned lock with `unwrap_or_else(|e| e.into_inner())` ([api/mod.rs:152-159](../src/Launcher/src/api/mod.rs)), and `on_ui` panics on purpose ([api/mod.rs:233](../src/Launcher/src/api/mod.rs)). `call` also turns a `spawn_blocking` worker panic into an error string ([main.rs:49-51](../src/Launcher/src/main.rs)). With abort, any panic in any IPC handler would kill the launcher, and it saves only some binary size. `opt-level = 3` would speed up serde parsing, at an estimated +10–30% exe size. Most of that gain disappears once fix 1 takes parsing off the critical path, so it is optional. Fat LTO with one codegen unit gives marginal startup gains for much slower builds. The `devtools` Cargo feature is on for release ([Cargo.toml:16](../src/Launcher/Cargo.toml)), although Tauri makes it opt-in for release builds ([Tauri config reference](https://v2.tauri.app/reference/config/)). Gate it behind a cargo feature for security reasons. Speed is not a reason, since WebView2 ships devtools in the runtime anyway.

Leave the WebView2 environment alone. Microsoft says cold start is a fixed cost of spinning up processes and disk caches, and it recommends keeping the user data folder on a fast local disk and using a single WebView ([MS Learn](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance)). The launcher does both: its data directory is under `util::data_dir()` ([main.rs:125-149](../src/Launcher/src/main.rs)), and it has one window. Microsoft also warns against disabling the GPU. The athas Tauri app removed `--enable-gpu-rasterization --ignore-gpu-blocklist` before merging, because those flags "bypass hardware safeguards" ([athas PR #728](https://github.com/athasdev/athas/pull/728)). Setting `additionalBrowserArgs` at all means re-adding wry's three default `--disable-features` flags ([Tauri config reference](https://v2.tauri.app/reference/config/)). No source documents a browser argument that shortens startup. Do not build a WebView splash screen either: Microsoft says it costs more than it hides. `modulepreload` for the five or so shell modules, and font `preload` with `crossorigin`, flatten the waterfall cheaply ([web.dev fonts](https://web.dev/learn/performance/optimize-web-fonts)). Assets are embedded and served from memory, so expect a small gain. A release-only esbuild bundle is the bigger version of the same idea, but it adds a build step for an unmeasured gain over lazy loading.

## Conclusion

The launcher's slowness is not a framework problem or a WebView2 problem. It comes from ordering: real work (the item-DB parse, CS2 discovery under a lock, eager page imports, an early `show()`) sits in front of the first meaningful frame, and repeated work (lock-held polls, refetch storms) follows every event. That means a release-build measurement should come before *and* after fix 1. Log the item-DB load time and the `cases.inventory` payload size on a real install. Those two numbers decide whether fix 1 matters most or merely a lot, and whether inventory paging (deferred here) belongs in the plan at all.

One structural point stands out. Fixes 1, 3 and 8 all follow the same rule: render from cached or default state immediately, then reconcile when the real data arrives. The codebase already uses this rule in places, in the `reload_db` swap, `useApi`'s stale-while-revalidate cache and the `tour.done` localStorage read. Applying it consistently to startup state, rather than adding new mechanisms, is the cheapest way to make the launcher feel instant.
